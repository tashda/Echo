Design rules, so new screens need no rework

Instead of adjusting screen by screen, we agree the rules once. They go into DESIGN.md in the repository and into one tokens file in the app. Agents read them before they add anything, and every CI build produces screenshots of all screens, so you review rules and not elements. The first draft follows. The component map is what an agent looks up when it needs a new control.

Rules carried over from Echo

  • Native first: use the system control when one exists.
  • Glass is for controls (dock, toasts, floating panels), never for content.
  • No glass on glass: selection inside a glass control is a fill.
  • Everything through tokens: no literal sizes or colours in views.
  • Motion explains change; no decoration.
  • Reduce Motion, Reduce Transparency and Increase Contrast must all look right.

When an agent adds something new

  1. Look it up in the component map. If it is there, use it as written.
  2. If not, pick the nearest native control and add a row to the map in the same change.
  3. Take sizes, colours and spacing from the tokens file. If one is missing, add the token first.
  4. Colour only to show whose turn it is, or a real problem.
  5. Check the CI screenshots in light and dark before marking it ready.
